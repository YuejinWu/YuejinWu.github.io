操作系统内存管理：从虚拟化到分页与TLB

第一部分：内存虚拟化简介

1.1 操作系统对共享资源的管理

操作系统的核心职责之一是管理共享资源，这体现在两个维度：

  1. 时间上共享：通过进程/线程调度，在时间上共享物理处理器。这是此前课程（CPU调度）的核心内容。
  2. 空间上共享：通过内存管理，在空间上共享物理内存。
    • 核心矛盾：物理内存永远不够用。历史上著名的错误预言是：“640 KB 对每个人都足够了”。
    • 解决方案：内存虚拟化。为每个进程提供一种抽象——私有的、连续的、可能比物理内存更大的地址空间。

1.2 背景与约束条件

  • 程序运行的必要条件：程序必须从磁盘等次级存储载入内存，并置于进程的上下文中才能被CPU执行。
  • CPU的访问范围：内存和寄存器是CPU可以直接访问的唯一存储空间。
  • 内存的视角：内存控制器只能看到由CPU发出的地址流以及读或写请求。
  • 性能鸿沟：
    • 寄存器访问仅需1个CPU时钟周期。
    • 内存访问需要多个时钟周期，会导致CPU流水线停顿。
    • 缓存（位于CPU芯片上）被引入，作为寄存器和内存之间的高速缓冲，以缩小性能差距。
  • 安全性要求：内存保护是确保多个进程正确、安全并发运行的必要条件，防止一个进程错误地访问或修改其他进程或操作系统的内存数据。

这种模型一次只能运行一个用户程序，内存利用率低，不支持多道程序。

1.4 多道程序与分时系统的需求

现代操作系统需要支持：

  • 多道程序设计：同时将多个批处理作业载入内存，当一个作业等待I/O时，CPU可以切换到另一个作业。
  • 分时系统：多个用户通过终端同时使用交互式进程，每个用户都感觉独占了机器。
    核心问题：如何在有限的物理内存中容纳多个进程的地址空间？

1.5 地址绑定：指令/数据与内存地址的关联

程序中的符号地址（如变量名）最终需要绑定到具体的物理内存地址。这个过程可以发生在三个不同阶段：

  1. 编译时绑定：
    • 前提：内存位置在编译前已知。
    • 编译器生成使用绝对地址的代码。
    • 缺点：如果程序的起始加载地址改变，必须重新编译。
  2. 加载时绑定：
    • 前提：编译时内存位置未知，但程序加载到内存时确定。
    • 编译器生成可重定位代码。加载器根据程序被加载到的实际内存起始地址，修改代码中的所有地址引用（重定位）。
  3. 执行时绑定（动态运行时绑定）：
    • 前提：进程在执行期间可能被换出内存，并再次换入到不同的物理地址。
    • 绑定延迟到运行时。每次访问内存时，通过硬件支持的地址映射机制（如基址寄存器）将逻辑地址转换为物理地址。
    • 优点：提供了最大的灵活性，是实现虚拟内存和进程迁移的基础。

1.6 用户程序生成与加载流程

一个用户程序从源代码到在内存中运行，经历了多个步骤：

  • 链接器：将多个目标模块和库合并成一个完整的可执行文件，解析模块间的符号引用。
  • 加载器：将可执行文件读入内存，进行地址重定位（如果采用加载时绑定），并创建进程的初始地址空间。

1.7 进程的地址空间

操作系统为每个进程提供一个逻辑上连续、私有的地址空间。典型的进程地址空间布局（自低地址向高地址）包括：

  1. 代码段 (Text Segment)：存放程序的机器指令，通常是只读和可执行的。
  2. 数据段 (Data Segment)：存放已初始化的全局变量和静态变量。
  3. BSS段 (Block Started by Symbol)：存放未初始化的全局变量和静态变量，程序加载时由系统初始化为零。
  4. 堆 (Heap)：用于程序运行时动态内存分配（如 malloc、new），向高地址增长。
  5. 栈 (Stack)：用于函数调用，存放局部变量、函数参数、返回地址等，向低地址增长。

1.8 为什么需要动态内存（堆和栈）？

  1. 内存需求未知：每个进程所需的内存量不同，用户输入、数据结构大小等在编译时无法预知。
  2. 避免浪费：采用保守的静态预分配策略会浪费大量内存空间。
  3. 支持递归和复杂控制流：程序通常包含函数调用、递归等，需要在运行时动态管理调用上下文。

1.9 函数调用与栈管理

当一个函数被调用时，编译器会在栈上为其分配一个调用帧或活动记录。

  • 存储内容：局部变量、函数参数、返回地址（如RIP寄存器值）、以及保存的调用者寄存器等。
  • 分配与释放：函数开始时分配栈空间，函数返回时释放。遵循后进先出原则，与函数调用/返回的顺序完美匹配。
  • 示例分析： 对于 called 函数的调用帧（假设栈从高地址向低地址生长），其内容顺序（地址从高到低）可能是：参数 b、参数 a、返回地址 RIP、局部变量 tmp。这个过程由编译器根据应用二进制接口自动生成代码管理，程序员无需关心。

1.10 动态数据结构：堆的管理

堆用于满足程序运行时大小和生命周期都未知的动态内存请求。

  • 接口：alloc(size)（如 malloc）创建对象，free(ptr) 释放对象。
  • 挑战：如何高效地管理一大块内存，处理不同大小、任意顺序的分配和释放请求，并减少碎片？
  • 管理主体：操作系统内核为每个进程分配一大块虚拟内存作为堆。实际的分配和释放细节由运行时库（如C库中的 malloc/free 实现）管理，其目标是在性能、可靠性和安全性之间取得平衡。

1.11 内存虚拟化：目标与挑战

操作系统通过虚拟内存系统为每个进程提供私有的地址空间抽象。

  • 核心目标：
    1. 透明性：对用户进程简单友好，使其认为自己独占一大片连续内存。
    2. 效率：地址转换和内存访问要快，时空开销要小。
    3. 保护：隔离进程地址空间，防止相互干扰，确保系统安全和正确。
  • 核心问题：如何在单个物理内存之上为多个进程建立这种大而私有的地址空间抽象？

1.12 解决方案：地址转换与硬件支持

答案是通过地址转换。

  • 基本思路：在进程运行时，将指令提供的虚拟地址转换为实际的物理地址。
  • 要求：每次内存访问（取指令、读/写数据）时都需要进行转换，以实现透明性。
  • 性能关键：转换必须非常快。
  • 硬件支持：内存管理单元是CPU的一个组件，专门负责执行高效的地址转换。

1.13 早期简单方案：动态重定位（基址-限长寄存器）

在介绍复杂的分页机制前，首先考虑一个简单模型，基于三个强假设：

  1. 每个进程的地址空间在物理内存中是连续存放的。
  2. 每个虚拟地址空间的大小小于物理内存大小。
  3. 所有地址空间的大小完全相同。

在此假设下，可以采用动态重定位技术：

  • 硬件：MMU包含两个特殊寄存器。
    • 基址寄存器：存放进程地址空间在物理内存中的起始地址。
    • 限长寄存器：存放进程地址空间的大小（上限）。
  • 地址转换过程：
    1. CPU发出虚拟地址 VA。
    2. MMU检查 VA < 限长寄存器值。若否，触发地址越界异常（段错误）。
    3. 若是，则 物理地址 PA = 基址寄存器值 + VA。
  • 操作系统职责：
    • 进程创建：在物理内存中为地址空间找一个连续的空闲区域，将基址和限长值存入进程控制块。
    • 进程切换：将新进程的基址和限长值加载到MMU寄存器中。
    • 内存管理：维护一个物理内存的空闲列表，记录哪些区域是空闲的。分配时在列表中寻找足够大的连续空闲块；释放时将内存块标记为空闲并可能合并相邻空闲块。

1.14 基址-限长虚拟化方法的局限性

尽管简单，但此方法存在明显问题，促使我们寻求更高级的方案：

  1. 内部碎片：进程地址空间内部，堆和栈之间可能存在大量未使用的“空洞”，造成浪费。
  2. 地址空间大小受限：必须小于物理内存。
  3. 内存分配效率：为进程寻找连续的空闲内存块可能导致外部碎片，尽管可以通过紧凑/压缩来减少，但移动大段内存开销巨大。

第二部分：分段内存管理

2.1 分段的基本思想

为了更精细地管理内存并减少内部碎片，引入了分段。

  • 核心思想：将进程的地址空间按逻辑单元（段）进行划分，如代码段、数据段、堆段、栈段。每个段在物理内存中独立存放，可以非连续。
  • 硬件支持：为每个逻辑段维护一对基址寄存器和限长寄存器（或边界寄存器）。
  • 优势：允许稀疏的地址空间。堆和栈之间未使用的巨大虚拟地址空间无需分配物理内存，只需在对应段的页表中标记为无效即可。

2.3 地址转换与段选择

  • 关键问题：给定一个虚拟地址，硬件如何知道它属于哪个段？
  • 解决方案：虚拟地址被划分为两部分：段号 和 段内偏移量。
    • 一种常见方法：使用虚拟地址的高几位作为段号。例如，使用最高2位区分4个段（00-代码，01-堆，10-栈，11-未用）。
  • 地址转换过程（简化）：
    1. 从虚拟地址中提取 段号 和 偏移量。
    2. 用 段号 作为索引，找到对应的 基址 和 边界（限长）。
    3. 检查 偏移量 < 边界。若否，触发段错误。
    4. 若是，则 物理地址 = 基址 + 偏移量。

2.4 处理栈段与共享段

  • 栈段的特殊性：栈向低地址增长。因此，其地址转换逻辑需调整。硬件除了基址和大小，还需要知道段的生长方向位。对于栈，偏移量的有效性检查及地址计算需要特殊处理（例如，有效偏移量范围可能是 [0, 大小)，但地址计算为 物理地址 = 基址 + (大小 - 1 - 偏移量)，或使用负向偏移）。
  • 支持共享：为了节省内存，允许不同进程的地址空间共享某些段（如相同的代码库）。需要在段表项中增加保护位（如读、写、执行），以控制访问权限。共享段的基址在不同进程中相同。

2.5 分段管理的操作系统职责与问题

  • 上下文切换：保存和恢复进程的段寄存器集合。
  • 动态段增长：当进程通过 malloc 或 brk/sbrk 系统调用请求更多堆空间时，操作系统可能需要增大堆段，这涉及到在物理内存中寻找空闲空间并更新段表。
  • 外部碎片：这是分段的主要缺点。段大小不一，经过多次分配和释放后，物理内存中会散布许多小的空闲块，虽然总空闲内存足够，但无法满足新段的大块连续需求。
  • 解决方案及其代价：
    • 紧凑/压缩：移动已分配的段，将所有空闲空间合并成一大块。缺点是内存复制开销巨大，且过程中必须暂停所有进程。
    • 更优的空闲空间管理算法：尝试在分配时减少外部碎片的产生。

第三部分：空闲空间管理

3.1 空闲空间管理问题

无论是管理物理内存中的可变大小段，还是管理进程堆中的可变大小内存块（malloc/free），都面临同一个核心问题：如何管理一组大小不一的空闲内存块（空洞）？

  • 目标：最小化外部碎片（可能以引入少量内部碎片为代价）。
  • 基本数据结构：使用链表来管理空闲块。每个空闲块包含其起始地址、大小，以及指向下一个空闲块的指针。

3.2 分配与释放策略

  • 分配 (alloc)：当请求大小为 N 的内存时，遍历空闲链表，找到一个大小 >= N 的空闲块。
    • 分割：如果找到的块大于 N，通常将其分割为两部分：一块大小为 N 分配给请求者，剩余部分作为一个新的、更小的空闲块放回链表。
  • 释放 (free)：将释放的内存块合并回空闲链表。为了有效合并，需要检查该块前后相邻的内存块是否也是空闲的。如果是，则合并为一个更大的空闲块。
    • 合并是减少外部碎片的关键。

3.3 分配策略算法

如何在空闲链表中搜索合适的块？常见策略：

  1. 首次适应：从链表头开始，选择第一个足够大的块。
    • 优点：简单、快速。
    • 缺点：可能在小块碎片前分配大块，导致链表开头留下许多小碎片。
  2. 下次适应：从上一次结束搜索的位置开始，选择第一个足够大的块。
    • 优点：比首次适应更均匀地扫描链表。
  3. 最佳适应：搜索整个链表，选择大小与请求最接近的块。
    • 优点：理论上产生最小的剩余碎片。
    • 缺点：需要遍历整个链表，速度慢；可能产生大量极小的、难以再利用的碎片。
  4. 最差适应：搜索整个链表，选择最大的块进行分配。
    • 目的：避免产生太多小碎片。
    • 缺点：可能过早耗尽大块内存，不利于后续的大请求。
  • 模拟结论：首次适应和最佳适应在减少碎片方面表现较好，而首次适应因简单快速更常被采用。

3.4 元数据开销与嵌入式空闲链表

  • 问题：管理空闲链表本身也需要内存来存储节点信息（地址、大小、下一个指针）。这部分内存从何而来？
  • 解决方案：将空闲链表的元数据（头部）嵌入到空闲块自身内部。即，每个空闲块的起始部分存储其大小和指向下一个空闲块的指针。已分配的块则只需在头部存储大小和验证信息（如魔数），返回给用户的是头部之后的地址。
  • 示例流程：
    1. 初始堆：一个大空闲块，头部信息存放在堆起始处。
    2. 分配：从空闲块分割一部分，设置分配块头部，更新空闲块头部（地址后移，大小减小）。
    3. 释放：将释放块的头部改为空闲块头部（含大小和下一指针），并尝试与相邻空闲块合并。

3.5 内核内存分配的特殊性与高级分配器

内核内存分配有其特殊需求：

  • 许多内核数据结构（如任务描述符、文件对象）大小固定且较小。
  • 某些设备DMA操作需要连续的物理内存。
  • 伙伴系统：
    • 核心思想：以 2的幂次方（如4KB, 8KB, 16KB...）为单位进行分配。
    • 分配：递归地将大块内存对半分割，直到得到能满足请求的最小幂次块。
    • 释放：释放时检查其“伙伴”（分割自同一父块的另一块）是否空闲。若空闲，则合并为更大的块，并递归尝试进一步合并。
    • 优点：有效避免外部碎片，合并高效。
    • 缺点：可能造成严重的内部碎片（例如，请求33KB会分配64KB）。
  • Slab分配器（用于Linux, Solaris）：
    • 针对内核对象进行缓存式分配。
    • 核心概念：
      • Cache：为每种内核对象类型（如 task_struct, inode）建立一个缓存。
      • Slab：一个或多个连续的物理页，被划分为多个同类型的对象槽。
      • Slab有三种状态：满、部分满、空。
    • 分配流程：请求某类对象时，优先从“部分满”的slab中分配；若无，则从“空”slab中分配；若无，则创建新的slab。
    • 优点：
      1. 几乎无内部碎片：对象大小与槽位精确匹配。
      2. 速度极快：对象预创建，分配只是标记状态位。
      3. 利用缓存局部性：同类型对象集中存放，提高缓存命中率。

第四部分：分页内存管理

4.1 分页：解决外部碎片的核心思路

分段的主要问题是外部碎片。一个根本性的解决思路是：放弃连续分配，改用固定大小的分配单元。

  • 基本概念：
    • 页帧：物理内存被划分为固定大小的块，称为物理页帧或页框。大小通常是2的幂次方（如4KB）。
    • 页面：进程的虚拟地址空间也被划分为同样大小的块，称为虚拟页面或页。
  • 核心特性：进程的虚拟页面是连续的，但操作系统可以将其映射到物理内存中任意不连续的页帧上。
  • 优势：
    1. 完全消除外部碎片：因为分配单元大小固定，任何空闲页帧都可以满足任何页面的分配需求。
    2. 内部碎片可控：最多浪费不到一个页面的大小。
    3. 简化空闲空间管理：只需维护一个空闲页帧列表。

4.2 页大小的权衡

页面大小是一个重要的设计选择：

  • 小页面（如512B）：
    • 优点：内部碎片小，内存利用率高。
    • 缺点：页表更大（需要更多条目），管理开销大，TLB覆盖的地址范围小。
  • 大页面（如4MB）：
    • 优点：页表更小，TLB效率高，管理开销小。
    • 缺点：内部碎片可能更大，不利于精细的内存共享。
  • 常见选择：折中方案，如 4KB，被许多现代系统（x86, ARM）采用。

4.3 地址结构

  • 虚拟地址 (VA)：由虚拟页号和页内偏移量两部分组成。
    • 偏移量字段的长度由页面大小决定（如4KB页面需要12位偏移量）。
    • 剩余的高位组成虚拟页号。
    • 示例：32位地址，4KB页 => 20位VPN + 12位偏移 => 地址空间4GB，共2^20个页面。
  • 物理地址 (PA)：由物理帧号和相同的页内偏移量组成。
    • 物理地址宽度决定PFN的位数。例如，24位物理地址，4KB页 => 12位PFN + 12位偏移 => 物理内存16MB。

4.4 页表与地址转换

  • 页表：操作系统为每个进程维护一个数据结构，存储在内存中，用于记录该进程的虚拟页到物理帧的映射关系。
  • 页表项：页表中的每个条目对应一个虚拟页，通常包含：
    • 物理帧号：该页所在的物理帧号。
    • 有效位：该映射是否有效（页是否在内存中）。
    • 保护位：读、写、执行权限。
    • 脏位：该页内容是否被修改过（对写回策略很重要）。
    • 访问位：该页是否被访问过（用于页面替换算法）。
    • 其他位：如用户/内核模式位。
  • 地址转换流程（概念上）：
    1. CPU发出虚拟地址 VA。
    2. MMU将 VA 分解为 VPN 和 Offset。
    3. 以 VPN 为索引，查找当前进程的页表，获取对应的页表项。
    4. 检查PTE的有效位和保护位。若无效或权限不足，触发缺页异常或保护错误。
    5. 从PTE中取出 PFN。
    6. 物理地址 PA = (PFN << 偏移量位数) | Offset。

4.5 线性页表及其问题

  • 线性页表：最简单的页表形式，是一个数组。数组下标是VPN，数组元素是PTE。
  • 致命缺陷——空间爆炸：
    • 页表条目数 = 虚拟地址空间大小 / 页面大小。
    • 例如：64位地址空间，4KB页 => 虚拟页数 = 2^(64-12) = 2^52。假设每个PTE 8字节，一个进程的页表大小 = 2^52 * 8 Bytes = 32 PB！这是完全不现实的。
  • 根源：线性页表为每一个虚拟页都分配了一个条目，即使该页从未被进程使用（如堆栈之间的空洞）。

第五部分：页表优化——更小的页表

5.1 优化方向：多级页表与倒置页表

为了解决线性页表过大的问题，主要思路是只为实际使用的虚拟页保存映射信息。两种主流技术：

  1. 多级页表：引入层次结构，像书本的“目录-章节-页”一样，只有被访问的“章节”才需要分配页表。
  2. 倒置页表：转换视角，只为物理内存中存在的映射（即已分配的页帧）建立页表。

5.2 多级页表

  • 核心思想：将虚拟页号 VPN 进一步划分为多个部分，每一部分作为一级页表的索引。
  • 示例（经典两级页表，32位系统，4KB页）：
    • 虚拟地址：10位(目录索引) + 10位(页表索引) + 12位(偏移量)。
    • 页目录：一个单独的页（4KB），包含1024个目录项。每个目录项指向一个二级页表的基址（或为空）。
    • 二级页表：每个二级页表也是一个4KB的页，包含1024个页表项。每个PTE指向物理帧。
    • 地址转换需要三次内存访问：访问页目录 -> 访问二级页表 -> 访问目标数据。
  • 优势：
    • 节省空间：如果虚拟地址空间的某个区域（如堆栈之间的大片空洞）没有使用，其对应的二级页表就无需分配。页目录中对应项标记为“无效”即可。
    • 支持稀疏的地址空间。
  • 劣势：地址转换速度比线性页表慢（需要多次访存），但通过TLB可以极大缓解。

5.3 x86架构的页表示例

  • 传统x86（32位，无PAE）：使用两级页表（页目录+页表），如前所述。
  • 物理地址扩展：为了支持超过4GB的物理内存，x86引入了PAE模式，页表项扩展为64位，并使用三级页表。
  • x86-64（64位长模式）：使用四级页表（PML4、页目录指针、页目录、页表），支持48位虚拟地址（256TB）。最新的五级页表扩展了虚拟地址到57位（128PB）。

5.4 倒置页表

  • 核心思想：页表的条目数不再与虚拟页数相关，而是与物理页帧数相等。每个条目记录占用该页帧的进程标识符和虚拟页号。
  • 工作原理：
    • 系统只有一个全局的倒置页表。
    • 给定虚拟地址 (PID, VPN)，需要搜索整个倒置页表，找到匹配 (PID, VPN) 的条目，其索引就是物理帧号。
  • 查找加速：线性搜索不可行。通常使用哈希表来加速查找。哈希函数以 (PID, VPN) 为输入，输出一个哈希值，指向一个哈希桶。在桶内进行链式查找。
  • 优势：
    • 页表大小恒定，仅与物理内存大小成正比，与进程数及虚拟地址空间大小无关。
    • 非常适合虚拟地址空间巨大但物理内存相对较小的系统。
  • 劣势：
    • 哈希冲突处理需要额外开销。
    • 共享内存实现更复杂。
    • 已被PowerPC、IA-64等架构采用。

第六部分：分页性能优化——翻译后备缓冲器

6.1 分页的性能挑战

即使采用多级页表减少了空间开销，但每次地址转换需要多次访问内存（访问各级页表），这会使内存访问速度下降数倍，无法接受。

6.2 TLB：地址转换的缓存

翻译后备缓冲器是MMU中一个小容量、极高速的硬件缓存，用于缓存最近使用过的页表条目。

  • TLB条目内容：包含VPN、PFN、有效位、保护位、脏位、ASID等。
  • 工作流程：
    1. CPU发出虚拟地址。
    2. MMU首先用VPN在TLB中并行查找（硬件实现，1个时钟周期）。
    3. TLB命中：直接获得PFN，与偏移量组合成物理地址，访问内存。整个过程只增加约1个周期的开销。
    4. TLB未命中：需要“慢路径”处理：根据当前页表基址寄存器，访问内存中的页表，找到正确的PTE，将其加载到TLB中，然后重试导致未命中的指令。

6.3 TLB未命中处理

谁负责处理TLB未命中？

  • 硬件管理TLB（如x86）：
    • TLB未命中完全由硬件处理。
    • 硬件知道页表格式（如多级结构），自动遍历页表，加载PTE到TLB。
    • TLB替换策略（如LRU近似算法）由硬件固定。
  • 软件管理TLB（如MIPS, SPARC）：
    • TLB未命中会触发一个特殊的TLB缺失异常。
    • 异常处理程序（操作系统内核代码）负责遍历页表，找到PTE，并通过专用指令将其写入TLB。
    • 操作系统可以灵活实现TLB替换策略。
    • 优势：更灵活，页表格式可由软件定义。

6.4 TLB上下文管理与ASID

  • 问题：进程切换时，TLB中缓存的都是旧进程的映射，对新进程无效。如何处理？
  • 方案一：清空TLB：在上下文切换时，通过一条指令使整个TLB无效（清除有效位）。简单但粗暴，新进程开始时将经历大量TLB未命中，性能有短期抖动。
  • 方案二：地址空间标识符：
    • 每个TLB条目增加一个ASID字段，标识该映射属于哪个进程。
    • CPU有一个当前ASID寄存器。
    • 地址转换时，硬件同时检查VPN匹配和ASID匹配。
    • 优势：不同进程的映射可以共存于TLB中，切换进程时只需更改当前ASID寄存器，无需刷新TLB，极大提升了进程切换性能和系统整体性能。

6.5 TLB性能分析

  • 命中率：TLB性能的关键指标。现代程序得益于局部性原理（时间局部性和空间局部性），TLB命中率通常很高（>99%）。
  • 有效内存访问时间：
    • 假设：内存访问时间 = 100 ns，TLB查找 = 0 ns。
    • 若TLB命中，EMAT = 100 ns。
    • 若TLB未命中，假设需要一次额外的内存访问来读取PTE，则EMAT = 200 ns。
    • 当命中率 = 99% 时，EMAT = 0.99*100 + 0.01*200 = 101 ns。仅比纯物理内存访问慢1%。
    • 这证明了TLB在极小开销下，使分页机制的性能接近于无分页系统。

6.6 页级保护与TLB

内存保护检查（读/写/执行权限）可以集成在地址转换过程中：

  • 慢路径（页表）：在访问页表获取PTE时检查保护位。
  • 快路径（TLB）：将保护位缓存在TLB条目中。在TLB命中的同时进行权限检查。如果违反（如试图写入一个只读页），则立即触发保护错误异常。这保证了保护检查不会成为性能瓶颈。

总结

从简单的基址-限长寄存器到复杂的多级页表配合TLB，操作系统内存管理的发展是一个不断在透明性、效率、保护和功能之间寻求平衡的过程。

  1. 虚拟化目标：为进程提供私有的、连续的地址空间抽象。
  2. 分段：按逻辑单元管理，减少内部碎片，但引入外部碎片问题。
  3. 分页：使用固定大小页面，彻底消除外部碎片，成为现代OS内存管理的基石。
  4. 页表优化：通过多级页表或倒置页表，解决页表自身过大的空间开销。
  5. TLB：利用高速硬件缓存缓存页表条目，将分页带来的性能开销降至极低。

最终形成的现代内存管理模型是：基于分页的虚拟内存系统，它结合了硬件MMU（含TLB）的高效支持和操作系统内核的复杂管理（处理缺页异常、页面置换、共享内存等），从而实现了高效、安全、灵活的内存共享与隔离。
