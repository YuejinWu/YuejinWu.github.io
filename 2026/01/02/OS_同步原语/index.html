操作系统同步原语：从竞争条件到管程与经典问题

第一章：竞争条件与互斥基础

1.1 跨线程通信与共享内存模型

在多线程环境中，线程间通信的基本模型是通过共享地址空间。一个典型范例是使用一个共享的、有界的缓冲区：

  • 线程1（发送者/生产者） 向缓冲区写入数据。
  • 线程2（接收者/消费者） 从缓冲区读取数据。
    操作系统为此类通信提供的基本接口可能是：
  • send(message): 如果缓冲区有空间，则插入消息；否则，阻塞调用线程直至空间可用。
  • receive(): 如果缓冲区有消息，则返回一条消息；否则，阻塞调用线程直至有消息可用。
    此模型实例化了经典的生产者-消费者问题。

1.2 竞争条件：定义、成因与危害

竞争条件指程序的输出或结果依赖于多个并发线程执行指令的相对时序或交错顺序。

  • 核心成因：当多个线程在没有适当同步的情况下，并发地对同一个共享变量执行“读取-修改-写入”的多步非原子操作时。
  • 详细示例：
    假设两个发送者线程A和B并发执行 in = in + 1（in 初始为0）。该高级语言操作通常对应多条机器指令： 可能的错误交错执行顺序：

1.3 临界区与互斥原则

为了解决竞争条件，我们引入临界区的概念。

  • 临界区定义：访问共享资源（变量、数据结构等）的那段代码区域。必须保证其执行具有原子性。
  • 互斥访问四原则（为正确实现临界区访问提供理论框架）：
    1. 空闲让进：当没有线程处于临界区内时，应立即允许一个请求进入的线程进入。
    2. 忙则等待：如果已有线程在临界区内，其他所有试图进入的线程必须在外面等待。
    3. 让权等待：等待进入临界区的线程应主动释放CPU（进入阻塞态），避免“忙等待”（自旋）浪费处理器资源。
    4. 有限等待：对任何一个提出进入请求的线程，其等待时间必须是有限的，避免“饥饿”。

1.4 锁：实现互斥的基本机制

锁（或称互斥锁）是一个共享变量，用作协调其他共享资源访问的标志。

  • 两个基本原子操作：
    • acquire(lock) / lock(): 尝试获取锁。若锁已被其他线程持有，则调用线程等待。
    • release(lock) / unlock(): 释放锁，使其他等待线程有机会获取。
  • 核心作用：通过用 acquire 和 release 操作包裹任意复杂的临界区代码，在逻辑上将其转换为一个原子操作。

早期有缺陷的实现尝试：

问题分析：acquire 操作本身包含对锁变量 L.state 的“检查-设置”多步操作，这又是一个临界区！两个线程可能同时检查到锁为 UNLOCKED，然后都将其设置为 LOCKED，从而同时进入临界区，违反了互斥原则。

关于“禁用中断”的讨论：

  • 在单CPU系统中，在临界区内禁用定时器中断可以防止线程被切换，从而实现原子性。
  • 局限性：
    1. 不适用于多CPU（多核）系统：禁用当前CPU的中断无法阻止其他CPU上的线程进入同一临界区。
    2. 安全风险：将禁用中断的权限交给用户线程是危险的。恶意或错误的用户线程可能禁用中断后不再启用，导致系统失去调度能力而崩溃。
  • 结论：禁用中断通常仅作为操作系统内核在特定场景下实现低级同步的一种手段，并非通用的用户级解决方案。

第二章：信号量

2.1 从互斥到同步

互斥锁解决了竞争条件问题，但并发编程中还有另一类问题：同步。

  • 同步定义：涉及两个或多个通信线程，一个线程需要等待另一个线程完成某项工作或达到某个状态（条件为真）后才能继续执行。
  • 经典问题：生产者-消费者问题。生产者不能在缓冲区满时写入，消费者不能在缓冲区空时读取。线程间需要协调“条件”何时成立。

2.2 轮询的低效与 sleep/wakeup 原语

初始的朴素解决方案（轮询/忙等待）：

缺陷：持续占用CPU进行无意义的循环检查，效率极低。

改进思路：引入 sleep() 和 wakeup(thread_id) 原语。

  • sleep(): 将调用线程的状态从运行态改为阻塞态，使其让出CPU。
  • wakeup(thread_id): 将指定线程的状态从阻塞态改为就绪态，使其有机会被调度执行。

初步使用 sleep/wakeup 的实现（存在缺陷）：

唤醒丢失问题：在消费者执行完 release(buffer_lock) 后、调用 sleep() 前的这个时间窗口内，生产者可能已经向缓冲区添加了消息并调用了 wakeup(consumerThread)。由于此时消费者尚未睡眠，这次唤醒信号就“丢失”了。随后消费者调用 sleep() 并可能永远无法被唤醒。

  • 根源：release() 和 sleep() 不是原子操作。
  • 解决思路：需要将释放锁和进入睡眠设计为一个不可分割的原子操作。这直接引出了信号量的设计。

2.3 信号量的概念与迪杰斯特拉的原语

艾兹格·迪杰斯特拉（Edsger Dijkstra）于1965年提出信号量及其两个原子操作：P() 和 V()（荷兰语缩写）。为便于理解，常称为 down()/up() 或 wait()/signal()。

核心思想：信号量维护一个资源计数器，并关联一个等待队列。

  • 类比：餐厅经理管理空闲餐桌数。
    • 客人到来 (down)：有空桌则计数减一并入座；无空桌则排队等待。
    • 客人离开 (up)：计数加一，并唤醒一个等待的客人入座。

2.4 信号量的两种定义与实现

定义一（非负整数信号量）:

  • 信号量 s 是一个非负整数。
  • down(s): 如果 s > 0，则 s--；否则，调用线程等待，直到另一个线程执行 up(s) 后再次尝试。
  • up(s): s++，并唤醒所有正在等待该信号量的线程。
  • 问题：up() 唤醒所有线程可能低效，且被唤醒的线程仍需竞争资源。

定义二（允许负值的信号量，更常用）:

  • 信号量 s 可为任意整数。
  • 物理意义:
    • s > 0: 表示可用资源的数量。
    • s = 0: 表示无可用资源，且无线程等待。
    • s < 0: 其绝对值表示正在等待该资源的线程数量。
  • 操作语义:
    • down(s): 原子地执行 s--。如果结果 < 0，则将当前线程状态改为 BLOCKED，并加入该信号量的等待队列。
    • up(s): 原子地执行 s++。如果结果 <= 0（说明有线程在等待），则从其等待队列中移除一个线程，将其状态改为 READY，并加入就绪队列。

二元信号量：

  • 可以完全替代互斥锁（自旋锁）的功能，且避免了忙等待。

2.5 使用信号量解决生产者-消费者问题

为大小为N的缓冲区设置三个信号量：

  • mutex: 二元信号量，初始为1，用于保证对缓冲区的互斥访问（解决竞争条件）。
  • empty: 计数信号量，初始为N，表示空闲缓冲区单元数量。
  • full: 计数信号量，初始为0，表示已占用的缓冲区单元数量。

方案A（错误方案，可能导致死锁）：

死锁场景分析：假设缓冲区已满。生产者执行步骤1 (down(mutex)) 成功获取 mutex。执行步骤2 (down(empty)) 时，由于 empty=0，生产者被阻塞在 empty 的等待队列中。此时，生产者仍持有 mutex。消费者试图执行 receive，第一步 down(mutex) 就会因为 mutex 被生产者持有而阻塞。双方互相等待，形成死锁。

方案B（正确方案）：调整 down 操作的顺序，先对资源信号量 (empty/full) 操作，再对互斥信号量 (mutex) 操作。

正确性解释：生产者在持有 mutex 之前先申请 empty。如果缓冲区满 (empty=0)，生产者会在 empty 上阻塞，而不会持有 mutex。此时消费者可以正常获取 mutex 并消费，消费后会执行 up(empty) 唤醒阻塞的生产者。这避免了死锁。

2.6 对锁实现的改进

基于TAS/CAS的自旋锁在锁被长期持有时会浪费大量CPU周期。更优的实现是：当 acquire() 发现锁已被持有时，将当前线程状态设置为 BLOCKED，并加入该锁的等待队列，然后让出CPU。当锁被释放时，再从等待队列中唤醒一个线程。

  • 需要维护的数据结构：waitingThreads（等待线程列表）、heldBy（当前持有锁的线程）。
  • 挑战：在实现 Sleep() 和 Wakeup() 逻辑时，仍需仔细处理竞争条件，确保正确性。这通常在操作系统内核或运行时系统的底层实现中完成（如BLITZ实验2的要求）。

第三章：管程与条件变量

3.1 信号量的局限性与管程的引入

尽管信号量功能强大，但正确使用它编写程序是困难的：

  • down() 和 up() 的调用顺序非常微妙，容易出错。
  • 难以避免竞争条件和死锁。
  • 需求：能否由编译器或编程语言提供更高级的抽象，自动生成正确的同步代码？管程应运而生。

3.2 管程的概念与特性

管程是一种高级同步构造，可视为一个特殊的“对象”或“模块”。

  • 封装性：管程内部的共享数据只能通过其声明的入口方法进行访问，对外部隐藏实现细节。
  • 互斥性：
    • 每个管程关联一个互斥锁。
    • 任何线程在调用管程的入口方法时，必须首先获取该互斥锁。
    • 因此，任何时刻最多只有一个线程能在管程内部处于活动状态（即执行入口方法）。

3.3 条件变量：解决管程内的同步问题

互斥锁保证了管程内一次只有一个线程，但如果这个线程发现运行条件不满足（如缓冲区空/满），它需要等待。如果它在管程内直接调用类似 sleep() 的操作，会因为它持有管程锁而导致其他线程永远无法进入管程来改变条件并唤醒它，造成永久阻塞。

条件变量是管程内部用于解决线程同步问题的机制。

  • 本质：一个等待队列，关联一个等待条件。
  • 三个核心原子操作：
    1. wait(): 调用此操作的线程释放管程锁，离开管程，并阻塞自己，进入该条件变量的等待队列。
    2. signal(): 唤醒在该条件变量等待队列中的一个线程。被唤醒的线程将在将来某个时刻重新获取管程锁后，从 wait() 调用之后继续执行。
    3. broadcast(): 唤醒在该条件变量等待队列中的所有线程。
  • 关键特性：wait() 操作原子地完成了“释放锁”和“进入睡眠”这两个动作，彻底解决了之前提到的“唤醒丢失”问题。

3.4 管程的语义：Hoare vs. MESA

当管程内的线程A执行 condition.signal() 唤醒等待线程B时，应该立即让B执行，还是让A继续执行？这引出了两种管程语义。

  1. Hoare 语义（由Tony Hoare提出）：

    • 规则：发出 signal 的线程A立即离开管程并等待（通常进入一个紧急队列）；被唤醒的线程B立即进入管程执行。
    • 优点：线程B被唤醒时，可以确保它所等待的条件仍然成立（因为A在发出信号后没有机会改变条件）。
    • 缺点：实现复杂，需要额外的上下文切换。线程A需要被保存状态，并在B退出管程后被重新调度执行。

  2. MESA 语义（Java synchronized 块和 wait()/notify() 采用此语义）：

    • 规则：发出 signal 的线程A继续执行，直到退出管程。被唤醒的线程B被移到管程的入口队列中，需要与其他线程竞争管程锁。
    • 优点：实现更简单，上下文切换更少，并发度可能更高。
    • 严重缺点：线程B被唤醒后、到它最终获得锁并重新进入管程的这段时间内，条件可能被其他线程改变而不再成立。
    • 核心要求：在MESA语义下，绝对不能使用 if 语句检查条件，必须使用 while 循环。被唤醒的线程在重新获得锁后，必须再次检查条件是否成立，如果不成立，则再次调用 wait()。

3.5 使用管程与条件变量解决生产者-消费者问题

与信号量方案的对比：管程方案将互斥（mutex）和资源计数（empty, full）的逻辑封装在了一起，通过条件变量 wait/signal 来表达同步关系，代码结构更清晰，更接近于高级语言思维。

3.6 读者-写者问题

  • 问题描述：多个并发线程共享一个资源（如文件、数据库）。线程分为两类：
    • 读者：只读取资源，不修改。
    • 写者：读取并修改资源。
  • 核心要求：
    1. 允许多个读者同时访问（读操作不互斥）。
    2. 写者必须独占访问（写操作与任何其他读/写操作互斥）。
  • 三种常见变体：
    1. 读者优先：只要有一个读者正在读，后续所有读者都可以直接开始读，写者必须等待所有读者（包括新来的）结束。
    2. 读写公平（如使用读写锁）：读者和写者按照请求到达的FIFO顺序获得访问权。写者等待时，新读者不能插队。
    3. 写者优先：如果一个写者在等待，那么新到达的读者必须等待，直到所有等待的写者完成。

使用信号量实现“读者优先”：

工作流程：wmutex 作为基本的互斥锁。第一个读者获取 wmutex，最后一个读者释放它。这保证了：只要有读者在读，写者就无法获取 wmutex；当读者数为零时，写者才能获取锁进行写操作。多个读者通过 rmutex 安全地更新 readers 计数。

3.7 并发程序中的常见错误类型

  1. 原子性违反：
    • 表现：本应原子执行的一段代码（临界区）被并发线程交错执行。
    • 示例：两个线程同时执行 counter++ 导致结果错误。
    • 修复：使用互斥锁保护临界区。
  2. 顺序违反：
    • 表现：线程A假设线程B已经完成了某项操作（如初始化），但实际上B可能尚未执行或未完成。
    • 示例：线程2读取线程1刚创建但尚未完全初始化的对象状态。
    • 修复：使用条件变量、信号量或屏障等同步机制来明确强制操作顺序。
  3. 死锁：
    • 表现：一组线程彼此循环等待对方持有的资源，导致所有线程都无法前进。
    • 示例：线程1持有锁A请求锁B，线程2持有锁B请求锁A。
    • 修复：
      • 规定全局的、一致的锁获取顺序。
      • 使用超时机制。
      • 避免嵌套持有多个锁。
      • 使用死锁检测与恢复算法（较复杂）。

第四章：经典同步问题剖析

4.1 哲学家就餐问题

问题描述

  • 5位哲学家围坐圆桌，每人面前一盘意面。
  • 每两位哲学家之间有一根筷子（共5根）。
  • 哲学家行为循环：思考 → 拿起左右两根筷子吃饭 → 放下筷子。
  • 筷子是独占资源。设计算法避免死锁和饥饿，并尽可能提高并发度（允许多人同时吃）。

错误方案分析

方案1（直接取筷）：

问题：死锁。若所有哲学家同时拿起左筷，则每人都在等待右筷，而右筷被邻居持有，形成循环等待。

方案2（全局互斥）：

问题：性能极差。任何时候只有一位哲学家能吃饭，完全丧失了并发性。

基于状态检查的信号量方案

核心思想：引入哲学家的状态（THINKING, HUNGRY, EATING）。仅当哲学家的左右邻居都不在 EATING 状态时，他才可以进入 EATING 状态。

  • 为每位哲学家设置一个信号量 sem[i]，用于在无法吃饭时阻塞。
  • 用一个互斥锁 mutex 保护状态数组 state[5]。

更简单的无死锁方案

通过破坏循环等待条件来预防死锁。让至少一位哲学家以不同的顺序取筷子。

原理：所有哲学家都先左后右，会形成循环等待（每个都持有左等右）。让一位哲学家先右后左，就打破了循环依赖链。此方案简单有效，且允许最多两位不相邻的哲学家同时吃饭。

4.2 理发师睡眠问题

问题描述

  • 理发店有一位理发师、一张理发椅和N张等候椅。
  • 理发师：
    • 若无顾客，则在理发椅上睡觉。
    • 若有顾客，则为其理发，理完后查看等候椅。
    • 若等候椅有顾客，则请下一位来理发；否则，继续睡觉。
  • 顾客：
    • 进门后，若理发师在睡觉，则唤醒他并理发。
    • 若理发师正忙，则找空等候椅坐下等待。
    • 若无空等候椅，则离开。

第五章：总结

5.1 同步原语对比

原语 核心思想 主要用途 优点 缺点
锁 (互斥锁) 二进制标志，实现互斥。 保护临界区，解决原子性违反。 概念简单，硬件支持高效。 仅解决互斥，无法表达复杂同步条件。
信号量 带计数的同步变量，关联等待队列。 解决资源分配类同步问题（如生产者-消费者），可同时实现互斥与同步。 功能强大、灵活。 使用困难，down/up顺序易错，易导致死锁。
条件变量 与管程锁配合使用的等待队列。 在管程内部，让线程等待特定条件成立。 与管程结合使用时代码清晰，更面向对象。 必须与互斥锁结合使用，不能单独使用。
管程 封装了数据、互斥锁和条件变量的高级抽象。 提供结构化、易于维护的同步代码编写方式。 由语言/编译器支持互斥，程序员专注条件同步，减少错误。 需要编程语言支持，不同的语义（Hoare/MESA）影响编程模式。
  • 等价性：理论上，锁、信号量、条件变量/管程三者可以互相实现，即它们具有同等的表达能力。
  • 性能考量：选择哪种原语取决于具体场景（临界区大小、竞争激烈程度、等待时间长短）。例如，短临界区可能适合自旋锁，而长等待操作则适合使用会让出CPU的信号量或条件变量。

5.2 核心问题解决模式回顾

  1. 生产者-消费者：信号量方案使用 empty、full 进行资源计数，mutex 保证互斥；管程方案使用条件变量 notFull、notEmpty 进行等待/通知。
  2. 读者-写者：通过区分读者和写者，利用计数器实现“多读互斥、写排他”的语义。“读者优先”方案通过第一个读者加写锁、最后一个读者解读锁来实现。
  3. 哲学家就餐：展示了如何通过破坏循环等待（改变取筷顺序）来简单避免死锁，也展示了通过状态检查与信号量实现的更复杂但可能更公平的方案。

5.3 并发编程的挑战

编写正确的并发程序本质上是困难的，因为它要求程序员：

  1. 精确识别所有共享数据和临界区。
  2. 为所有临界区选择合适的同步机制（锁、信号量等）。
  3. 正确管理同步机制的获取与释放顺序，以避免死锁和顺序违反。
  4. 在性能（并发度）与正确性之间做出权衡（如自旋等待 vs. 阻塞睡眠）。

这份讲义系统梳理了从底层硬件原子指令到高层管程抽象的完整知识链条，并结合经典问题剖析了各类同步原语的应用与陷阱，为理解和设计并发程序提供了坚实的概念基础与实践指南。
